# Проверка защиты игровой экономики

**Что проверялось:** требования кейса §5.6 и §8 («Защита от накрутки», «Повторные запросы и одновременные действия»)
и критерий §10 «Жюри проверяет, что повторные запросы, изменение клиентских данных и одновременные действия не позволяют
нарушить игровые правила».

**Код:** ветка `feat/final-qa-demo`, коммит `0be4eed`.

**Как проверялось:**
1. Автотесты backend: `cd backend && npm test` — 125 из 125. Атаки собраны в `backend/tests/security.test.js`
   (11 тестов, демо-сервер на `createApp` и управляемых часах, параллельные запросы — настоящие HTTP-запросы к слушающему
   серверу) и `backend/tests/sandbox.test.js` (12 тестов). Отдельный прогон этих двух файлов — 23 из 23.
2. Скрипт `backend/scripts/cheat-check.mjs` против живого демо-сервера на реальных часах:
   `node backend/src/server.js --demo` с `TOMATO_STATIC_DIR=frontend/dist`, порт 8799.
   Команда: `cd backend && node --disable-warning=ExperimentalWarning scripts/cheat-check.mjs --api http://localhost:8799`.
   Результат: **24 из 24 атак отражены**, код выхода 0. Повторный запуск через `npm run cheat-check -- --api http://localhost:8799`
   дал тот же итог за 7 с.

Сокращения: `B/` = `backend/src/`, `bt/` = `backend/tests/`.

## Общие механизмы

| Механизм | Где |
|---|---|
| Сервер — единственный источник наград. XP и монеты меняются только в `grant` и `spend` | `B/services/game.js:26-58` |
| Идемпотентный журнал наград и трат: `UNIQUE(user_id, key)`, ключи вида `focus:<sessionId>`, `ach:<id>`, `node:<room>:<team>:<node>`, `challenge:<room>:<team>`, `upgrade:<id>:<level>`, `td:build:<requestId>` | `B/db.js:38-48`; `B/services/game.js:28-32,52-56,93,154,173,286`; `B/services/td.js:308,335` |
| Баланс не уходит в минус: условие в `UPDATE` и `CHECK` в схеме | `B/services/game.js:48-51`; `B/db.js:16-17` |
| Не больше одной активной фокус-сессии: частичный уникальный индекс | `B/db.js:101` |
| Транзакции `BEGIN IMMEDIATE` и savepoint-ы; события WebSocket уходят только после COMMIT и отбрасываются при откате | `B/db.js:251-282` |
| Время, длительность и цены задаёт сервер; лишние поля тела запроса игнорируются | `B/services/rooms.js:251-292` (длительность из `room.focus_sec`); `B/services/game.js:285`; `B/catalog.js` |
| По WebSocket клиент может отправить только `auth`, `subscribe`, `unsubscribe`, `heartbeat`, `ping` и голосовые сигналы; остальное — `UNKNOWN_EVENT`. Ограничение частоты: 30 сообщений в секунду, при превышении закрытие с кодом 4429 | `B/ws/hub.js:56-109` |
| Песочница демо-режима: демо-комнаты только для песочных аккаунтов и наоборот | `B/services/rooms.js:47-52` |

Обработчики выполняются в одном процессе Node, а `node:sqlite` синхронен, поэтому внутри процесса запросы не
перемежаются. Ограничения схемы (UNIQUE, CHECK, частичный индекс) защищают инварианты и независимо от этого.
Работа нескольких инстансов не проверялась (см. раздел «Что не проверено»).

## Что не проверено и известные ограничения

- **Несколько инстансов backend.** Защита от гонок рассчитана на один процесс с одной SQLite-БД. Поведение при нескольких процессах на одной БД и с внешней шиной не проверялось.
- **Нагрузка.** Нагрузочного тестирования не было.
- **Регистрация без ограничений.** `POST /api/users` не ограничен по частоте и не требует пароля (`B/http/routes.js:27`). Мульти-аккаунты возможны; лимиты наград действуют на каждый аккаунт отдельно. Общего rate-limit для HTTP нет, для WS есть (`B/ws/hub.js:61,66`).
- **Присутствие.** Heartbeat можно имитировать скриптом. Кейс прямо говорит, что система не обязана доказывать, что пользователь учился.
- **Мини-игра.** Награды Tower Defense (раунды и дуэли) не требуют фокус-сессии. Участие засчитывается за старт, постройку или улучшение (`B/services/td.js:164`). Награды ограничены суточными потолками (п. 10).
- **Подсказки UI не являются правилами.** Лимиты и кулдауны интерфейс показывает по `/api/config`, но проверяет их только сервер.
