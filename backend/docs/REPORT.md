# Tomato — итоговый отчёт

## 1. Первоначальное состояние
* `backend/` — **пустая папка**: сервера, БД, API, WebSocket, пользователей, комнат, таймера — не было.
* `frontend/` — Vite + React + Tailwind + shadcn. Из игрового кода — «кликер с аксолотлем» (локальный
  `GameContext`, всё в `localStorage`, к кейсу отношения не имеет) и добавленный ранее компонент
  `components/tomato/TomatoApp.tsx` (Welcome → Settings → Focus Room, Framer Motion). `TomatoApp` целиком
  локальный: таймер на клиенте, без сервера. Тестов не было, CI собирает только фронтенд-образ.
* Статус функций кейса: пользователи, комнаты, общий таймер, личные задачи, история, XP/уровни/валюта,
  улучшения, достижения, командное испытание, помощь/пакости, защита экономики — **отсутствовали**
  (на фронтенде были только макет таймера и несвязанная локальная игра).

## 2. Выполненные изменения
Реализован backend с нуля (P0 + P1 + минимум P2), клиентский слой и документация.

## 4. Архитектура
```
Браузер (любой UI) ──REST──▶ http routes ─▶ services (users/rooms/game/social) ─▶ SQLite (node:sqlite, WAL)
        ▲                                                  │ db.emit (после COMMIT)
        └────────────WebSocket (/ws)◀──────── Hub ◀────────┘
Планировщик 500 мс: переводит фазы по меткам времени; корректность не зависит от него (lazy advance).
```
Подробности и обоснования — в `backend/README.md`.

## 6. Тестирование
Запущено: `npm test` в `backend/` — **42 теста, 42 прошли, 0 упало** (≈15 с, управляемые часы, без системного времени).
Также выполнено вручную: `npm run demo` на реальном сервере с `TOMATO_DEMO=1` (реальные часы, FOCUS=10 BREAK=8) —
все проверки сценария пройдены; запрос `/api/health` и `POST /api/users` через Vite-прокси; `tsc --noEmit` фронтенда.

Покрытие 15 тестов из задания: 1 — rooms; 2, 3, 12, 15 — timer (+ws для реконнекта); 4, 5, 6, 7, 8, 14 — economy;
9 — team; 10 — social; 11 — persistence; 13 — rooms; 12/14 по WebSocket — ws; демо-режим — demo.

Что находили тесты: при первых прогонах упало 4 теста. В трёх виноваты сами тесты (не учтён бонус монет за достижение
«Прокачка»; цель испытания достигается за 6 сессий, а не 5; неверная длительность в WS-тесте). Одна проблема была
реальной в коде: нестабильный порядок участников при одинаковом `joined_at` — исправлено сортировкой по `rowid`.

Frontend (`cd frontend && npm test`, vitest): **16 тестов, все проходят** — утилиты (`format.test.ts`), REST-клиент на
подменённом `fetch` (`client.test.ts`) и интеграционные тесты клиента против настоящего backend в памяти с
управляемыми часами (`integration.test.ts`: комната, вход, синхронное время, награды, ошибки, WebSocket с обрывом и
автоматическим восстановлением). Проверено «мутациями»: намеренная порча идемпотентности наград, фазы пакостей, grace-периода
и формата времени ломает тесты (потом код возвращён). UI-компоненты автотестами не покрыты — проверялись вручную в браузере.

Не проверялось: нагрузка, несколько процессов, браузерный UI поверх нового клиента (клиентский слой
проверен только компиляцией и прокси-запросами), работа в Docker/CI.

## 7. Оставшиеся проблемы и ограничения
* **Временный UI подключён к backend** (`TomatoApp.tsx` на `TomatoClient` + `useTomatoRoom`): регистрация по имени,
  создание комнаты / вход по коду, серверный таймер, старт/досрочный выход, участники и статусы, прогресс команды,
  XP/монеты, «Бонус»/«Туман» на перерыве, уведомления о наградах, восстановление комнаты после перезагрузки.
  Проверено вручную в браузере вместе со вторым игроком-скриптом. Также в UI: «Профиль» (улучшения с покупкой, достижения, история,
  переключатель пакостей), «Щит»/«Стикер», отметка результата сессии — проверено вручную в браузере. Старый кликер (`/game`) хранит
  прогресс в `localStorage` — он не часть серверной экономики.
* **Voice Chat** не реализован (не требуется кейсом); Mute/Deafen — только UI.
* **Tower Defense, Team A/B, PvP** не реализованы: есть `team_key` в схеме, `GET /rooms/:id/game` (производные
  параметры, статус `preview`) и описание точки расширения. Действий игры/API башен нет.
* Один процесс: WebSocket-рассылка в памяти. Инварианты в БД сохранятся, но для нескольких инстансов нужна шина.
* Нет паролей/восстановления: токен в `localStorage`; потерян токен — потерян аккаунт. Нет общего rate-limit
  на регистрацию и HTTP (есть лимиты на соц-действия и WS-сообщения).
* Присутствие подтверждается heartbeat-ом, его можно имитировать скриптом — кейс не требует доказательства учёбы.
* `node:sqlite` помечен experimental в Node 22–24; Dockerfile/CI для backend не добавлены (текущий CI собирает
  только фронтенд-образ).
* Демо-режим даёт награду как за 25 минут (документировано, включается только флагом сервера).
* Опоздавший участник наблюдает до следующего цикла; хост должен запускать цикл вручную (авто-цикла нет).

## 8. Готовность к замене Frontend
Всё состояние и действия доступны через REST+WS (`docs/API.md`); экраны Welcome/Settings/Focus/Road Map
обеспечены данными: `room.phase/remainingMs`, `members[]`, `challenge.nodes/edges` с координатами, `me.allowedActions`.
Снимок комнаты всегда восстанавливается (`GET` или повторный `subscribe`), поэтому анимации переходов не теряют
состояние. Руководство — `docs/FRONTEND_INTEGRATION.md`.

## 9. Готовность к защите
MVP-пункты критерия готовности (все продемонстрированы тестами/демо-скриптом):
несколько игроков в комнате ✔; общая синхронизированная сессия ✔; досрочный выход одного ✔; награды только
выполнившим ✔; XP/уровень/улучшение ✔; прогресс общего испытания ✔; достижение цели и командная награда ✔;
помощь и пакость ✔; достижения и сохранение прогресса ✔; повторные запросы / подмена клиентских данных /
одновременные действия ✔.
Дополнительно (не MVP): Road Map как карта, демо-режим, клиентский слой. Не сделано: Voice, Tower Defense, PvP.
Для демонстрации: `TOMATO_DEMO=1 npm start` + фронтенд (чекбокс «Демо-режим» в настройках) и/или `npm run demo`.

## Дополнение: этап 3 — Road Map
* Backend: этапы карты фиксируются сервером (`team_nodes`, `reachedAt`), этапная награда выдаётся один раз
  (`node:<room>:<team>:<node>`), событие `node_reached`, снимок карты расширен (`next`, `segment`, `teams`, `reward`, `progress`).
* **Командный режим Team A / Team B** (`teamMode:true`): автобаланс, смена команды до старта цикла, раздельные очки и этапы,
  гонка к цели (победитель — первая команда; при одновременном финише больше очков, равенство — ничья), победная награда
  только победителям и один раз, помощь только своей команде. Миграция БД аддитивная (`ALTER TABLE … ADD COLUMN mode`, проверена
  на «старой» схеме).
* Тесты: `roadmap.test.js` (7) и `teams.test.js` (8); всего backend — **57 тестов, все проходят**. Ожидания ранее написанных
  тестов изменились осознанно: в комнате из двух игроков первая сессия даёт 2 очка → этап «Лес знаний» → +25 XP.
  Мутационная проверка: сломанное правило «награду получает только первая команда» тесты ловят.
* Frontend: `RoadMap.tsx` (маркеры команд, плавный переезд, режим A/B), интеграция с Focus Room, запоминание открытой карты;
  тесты vitest — **30, все проходят** (утилиты, клиент, интеграция против настоящего backend, компонент карты).
* Остаётся: ветвление маршрута (карта линейная, 4 узла), боевая система / Tower Defense (не требуются), голосовая связь.

## Дополнение: этап 4 — Tower Defense на перерывах
* **Движок** (`src/td/engine.js`): чистая детерминированная симуляция (шаг 0.25 игровой секунды): маршрут, 3 типа башен (лучник,
  пушка по площади, мороз с замедлением), 4 типа врагов, 4 этапа с волнами, 3 уровня башен. Баланс откалиброван и закреплён тестами
  (без башен — поражение, «выиграть, ничего не построив» нельзя, каждая следующая башня не ухудшает результат, сложность растёт по этапам).
* **Сервис** (`src/services/td.js`) и таблицы `td_towers`, `td_rounds`, `td_actions`, `td_duels`. Игра доступна только в фазе Break;
  симуляция идёт по серверным меткам времени (переживает перезапуск); раунд один на команду за перерыв и ограничен перерывом
  (короткий перерыв — ускорение игры, но не медленнее реального времени); по окончании перерыва / пропуске / закрытии комнаты раунд
  закрывается как `expired` без награды — учёба важнее. Башни команды сохраняются между перерывами.
* **Экономика:** башни и улучшения стоят Tomato Coins строителя (цены только из каталога), `spend()` не даёт уйти в минус,
  `requestId` защищает от повторов и гонок. Награда за победу — только участникам раунда, один раз, с суточным потолком; бонус ×1.5 за
  первое прохождение этапа; HP базы и урон берутся из улучшений игроков («Крепкие стены», «Усиленные башни»).
* **Road Map:** этапы открываются узлами команды (`camp` всегда; `forest`, `bridge`, `fortress` — после прохождения узла).
* **Team A/B:** у каждой команды свои башни и раунд на общей карте этапа; дуэль (оба сыграли один этап) разрешается сервером,
  победителю бонус; помощь только своей команде (этап 3) сохраняется.
* Достижения: «Строитель», «Оборона держится». REST `/td`, `/td/join|start|build|upgrade`; WS `td_state`, `td_round_started`,
  `td_round_finished`, `td_tower_built|upgraded`, `td_duel_result`.
* Тесты: `td-engine.test.js` (9), `td.test.js` (17) — всего backend **83 теста, все проходят**; frontend **41 тест**
  (компонент игры 9, интеграция клиента с реальным backend). Мутационная проверка: снятие ограничения «только на перерыве»,
  награда всем вместо участников, отсутствие защиты `requestId`, победа без убитых врагов — тесты падают.
* Проверено в браузере на живом сервере: постройка, раунд с волнами, победа с серверной наградой, закрытие игры после перерыва,
  режим A/B (соперник, ничья в дуэли).
* Не сделано / ограничения: продажа башен, несколько карт, враги с особыми способностями, звук; во время раунда башни другого
  игрока можно улучшать (общая оборона команды) — это осознанное правило. Ранее заявленный в отчёте этапа 3 перенос уведомлений
  вниз-влево на деле не был применён — исправлено только сейчас.
